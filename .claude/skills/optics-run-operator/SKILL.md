# Optics run operator

By default (`decision_mode` "fixture") a run started here is the OFFLINE RULE FIXTURE (replay provider, no model call, dry-run execution with motions_sent=0). It is not a model-designed experiment and not real mechanical motion. Say so in every report. If the user wants the agent itself to design, test, review and repair (`start_run` with `decision_mode="agent"`; the run stops at `awaiting_decision`), use skill `optics-agent-decide` for the whole run; the monitoring and reporting steps below still apply. OpenAI-provider runs exist only in the web panel and are not controlled here.

1. Start: call `start_run(client_request_id, request)` with a fresh, descriptive `client_request_id` (reuse the same id only to retry the identical request; the same id with a different body is an error). Do not pass `team_fault` or `algorithm_options` unless the user asks for a fault scenario. There is no provider option; never try to select a cloud model. The only choice is `decision_mode` ("fixture" by default, "agent" only for `optics-agent-decide`).
2. Monitor with `get_worker_error(run_id)` (optics-runs, read-only) together with `get_run(run_id)` (optics-evidence). A run is finished ONLY when `get_worker_error` reports `active == false` AND the stored `status` is terminal (`algorithm_passed`, `failed`, `stopped`, `paused`, `awaiting_review`, `awaiting_decision`, or `interrupted` with nothing active; `awaiting_decision` is an agent-decided run waiting for an answer, handled by `optics-agent-decide`, and `continue_run` is refused until a decision is submitted). Never decide from `status` alone: the stored status can read `paused` or `stopped` while a worker is still executing (a pause/stop only takes effect at the next node boundary) and `queued`/`running` while nothing executes it. While `active == true`, keep polling; `control_request` shows a pending pause/stop, and `display_state` is `waiting_for_worker` (queued behind the single worker, or blocked on the runtime lock; a pause/stop requested in that window may be discarded by the worker, so check the outcome afterwards), `executing`, `pause_requested`, `stop_requested` or `resuming`. With `active == false`, `display_state` is the stored status, except `not_executing_here` (stored status says `running` but this server is not executing it: it may be running in another process such as the CLI, or have been interrupted by a restart). Report `not_executing_here`; do not start a duplicate run and do not call it orphaned. Check `stage`, `attempts`, `retry_counts` and `error` from `get_run` each time; a previous failure is not the attempt currently running. `get_run` only copies run.json; it is not verified. A non-null `worker_error` means the background worker crashed and the run is not progressing (kept for this server process only); report it. `get_worker_error`, `continue_run`, `pause_run` and `stop_run` only act on runs created through `start_run` (offline replay runs and agent-decided runs); on any other run, including runs created in the web panel, they return a refusal: report it, do not work around it. When optics-runs is the panel-hosted endpoint (`mcp-panel.example.json`), `active` is the panel's real state and `continue_run` on an executing run is refused as a conflict.
3. Pause or stop only on request: `pause_run(run_id)` / `stop_run(run_id)` act at the next node boundary. Before resuming an `interrupted` (or any non-paused) run, you MUST call `get_execution_status(run_id)` (optics-evidence). Only if it returns `not_started` may you call `continue_run(run_id)`. If it returns `unknown`, STOP: do not call `continue_run` and switch to `optics-execution-unknown`. If it returns `accepted` or `rejected`, do not resume; report it. A `paused` run that never reached execution may be resumed with `continue_run(run_id)` after the same check. Do not use `continue_run` on a failed run, and never to retry an execution whose result is unknown.
4. If status is `awaiting_review`: do NOT approve anything (no tool exists for it). Report `plan_sha256` from `get_run` and hand off to a human reviewer.
5. When finished, call `get_acceptance_summary(run_id)` and `verify_run_artifacts(run_id)`; report both. Describe `algorithm_passed` as "workflow complete" only when `get_acceptance_summary` says so and `verify_run_artifacts` is `ok` (a run.json that says `algorithm_passed` while verification fails is NOT complete; report the `issues`), list `core_unaccepted` and `deferred_physical`, and state `physical_verified`. Never say "all requirements verified".
6. If status is `failed` or `stopped`, hand over to `optics-failure-triage` with the run_id.
